# ADR 01 - Defining the Architectural Pattern for the new MVP

## Status: Proposed

## Context

Atualmente a Vida Cristã tem um problema grave de rastreabilidade de fluxo financeiro. Atualmente:

Editora → UIECB → Associações → Supervisora → Cliente Final

Entretanto o dinheiro está pulando etapas e as informações não acompanham o dinheiro.

Problema Central: não existe vínculo entre pedido, comprador e pagamento.

Resultado:

- Não dá para auditar
- Não dá para conciliar
- Não dá para saber inadimplência real
- Não dá para gerar relatórios e KPIs

Objetivo:

** Todo pagamento precisa nascer de uma intenção de compra registrada no sistema **

Deve-se garantir que todo pagamento tenha um ID rastreável.

## Decision

O MVP adotará a Arquitetura de Monólito Modular, com base no cenário. Não está sendo construído um sistema de venda e sim um sistema de conciliação financeira e rastreabilidade.

### Baixo volume de usuários

Considerando o fluxo de vendas atual, o usuário do sistema será majoritariamente as Supervisoras. O número total de Supervisoras atualmente é inferior a 200 usuários. O baixo volume não demanda grandes requisitos de Elasticidade e Escalabilidade, nem a necessidade de um sistema altamente desacoplado, como o de microsserviços.

A adoção de Monólito Modular permite que, havendo necessidade, o sistema possa escalar, graças a modularidade, e em casos extremos, migrado para Microsserviços.

### Evitar Overengineering

Embora utilizemos transações via PIX na aplicação, uma Arquitetura Orientada a Eventos seria exagerada. É possível garantir consistência, rastreabilidade e reação a eventos em Monolito Modular.

Além do baixo volume de usuários, o time de suporte é pequeno e haverá integração com apenas uma forma de pagamento (PIX).

O que precisa ser garantido:

- Idempotência: O webhook do PIX pode chegar duas vezes

- Consistência: Pedido e pagamento precisam estar sincronizados

- Rastreabilidade: É necessário auditar tudo.

** Ante o exposto: A arquitetura não precisa ser orientada a eventos, mas a modelagem sim. **

É possível aplicar eventos na arquitetura escolhida através de Eventos Internos como PedidoCriado, PagamentoGerado e PagamentoConfirmado.

1 - Criar Pedido
2 - Emitir evento interno PedidoCriado
3 - Módulo de pagamento reage gerando PIX
4 - Webhook chega
5 - Emitir PagamentoConfirmado
6 - Atualiza o pedido

A adoção de Monólito Modular permite que, havendo necessidade, o módulo de pagamentos possa comunicar com uma fila e transformar eventos internos em eventos reais (RabbitMQ/Kafka).

### Módulos do MVP

- Auth: Login e Controle de Acesso
- Pedidos: Criar pedido e Consultar pedido
- Pagamentos: Gerar PIX, Webhook, Conciliação
- Catálogo: Revistas disponíveis para venda
- Administração: Painel do SuperAdmin

### Entidades do MVP

O Banco precisa garantir:

- Pedido → Pagamento (1:1)
- Usuário → Pedido (1:N)
- Contexto organizacional no momento do Pedido 

#### Usuário

- id
- nome
- email
- senha_hash
- tipo (ADMIN, SUPERVISORA, MEMBRO)
- associacao_id
- regiao_id

#### Região

- id
- nome

#### Associação

- id
- nome
- regiao_id

#### Revista

- id
- edicao
- preco
- img

#### Pedido

- id
- usuario_id
- associacao_id
- regiao_id
- revista_id
- quantidade
- valor_total
- status (PENDENTE, PAGO, CANCELADO)
- created_at

#### Pagamento

- id
- pedido_id
- valor
- status (GERADO, CONFIRMADO)
- metodo
- txid_pix
- created_at
- confirmed_at

Permite idempotência via txid_pix e para o MVP será utilizado apenas 1 pagamento por pedido.

### Relacionamento das Entidades

- Um Usuário pode realizar vários pedidos
- Um Pedido pertence a um único Usuário
- Um Pedido possui exatamente um Pagamento
- Uma Associação pertence a uma Região

### MVP que será entregue

- Login
- Cadastro de Usuário
- Criar pedido
- Gerar Pix
- Confirmar pagamento automaticamente
- Tela de consulta de pedidos

### Critério de Sucesso

** Conseguir saber exatamente quem comprou, quem pagou e quem não pagou **

## Consequences

Um novo fluxo de vendas será implementado:

- Usuário entra na página
- Faz login
- Cria um pedido
- Sistema gera cobrança
- Usuário paga
- Sistema recebe confirmação
- Pedido vira PAGO automaticamente

Informações disponíveis: quem comprou, quanto comprou e quem pagou.
